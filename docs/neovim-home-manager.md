# Neovim и Home Manager

Рабочая заметка для обсуждения. Источник Neovim и порядок перехода ещё не
утверждены; этот документ ничего не устанавливает и не меняет на машинах.

## Текущее состояние

- Flake фиксирует `gakawarstone/nvim` на `6cc0d7d`. На ноутбуке Home Manager
  подключает модуль из этого input, а `nix/home/gws/editor.nix` заменяет его
  источник конфигурации на тот же input с Kotlin-патчем. Модуль также
  устанавливает Neovim и инструменты разработки.
- Submodule `configs/nvim/.config/nvim` указывает на тот же репозиторий, но
  закреплён на `ae8ee55`. Это предок `6cc0d7d`, который содержит ещё 44
  коммита, включая модуль Home Manager. Шаблон установщика Arch не включает
  Neovim; локальный выбор установщика может отличаться от шаблона.
- На ПК `~/.config/nvim` сейчас является отдельной Git-копией на `6cc0d7d` с
  изменённым `lazy-lock.json`. Перед передачей пути Home Manager нужно вместе
  разобрать эти изменения. Копия остаётся нетронутой.
- Standalone Home Manager для Arch готовится отдельно. Его интерфейс и состав
  пока не нужно считать утверждёнными в этом PR.

## Варианты единого источника

| Источник | Что даёт | Что нужно решить |
| --- | --- | --- |
| Отдельный репозиторий через flake input | Уже используется ноутбуком; обе машины могут брать одну ревизию из общего `flake.lock`. История Neovim остаётся отдельной. | Как разрабатывать конфигурацию локально и обновлять input; что делать с submodule после перехода. |
| Submodule в dotfiles | Отдельная история Neovim и редактируемый checkout; ревизия фиксируется gitlink. | Как использовать одну и ту же ревизию в Nix и на Arch, включая получение содержимого submodule при оценке flake. Сейчас submodule и input расходятся. |
| Файлы внутри dotfiles | Одна рабочая копия и один коммит для настроек и интеграции. | Как перенести историю Neovim и сохранить при необходимости его самостоятельное использование. |

Первый вариант требует меньше изменений в работающей конфигурации ноутбука,
но выбор остаётся за пользователем. В любом варианте отдельно выбирается
способ применения: снимок в Nix store или ссылка на редактируемую рабочую
копию. Flake input сам по себе не решает, как обновлять плагины и их lock-файл.

## Что проверить перед переключением

1. Разобрать локальный `lazy-lock.json` на ПК и решить, какие изменения
   сохранить. Не заменять и не перемещать `~/.config/nvim` до отдельного
   согласования перехода.
2. Проверить обновление `lazy-lock.json`: источник ноутбука находится в Nix
   store, а значит, не предназначен для записи. Плагины и их состояние нужно
   рассматривать отдельно от закреплённой ревизии исходной конфигурации.
3. Согласовать владельца `~/.config/nvim` на каждом хосте и исключить конфликт
   со Stow и существующими файлами. Не удалять submodule без совместного решения.
4. Сохранить Kotlin-патч и набор инструментов ноутбука, пока не проверена их
   замена. При обновлении input проверить применимость патча и возможность его
   удаления только после включения соответствующих изменений в источник.
5. Учесть, что модуль Neovim устанавливает `NVIM_NIX=1`: конфигурация в этом
   режиме пропускает автоматическую установку инструментов через Mason. На Arch
   нужно проверить наличие нужных языковых серверов и форматтеров в PATH.
6. После появления standalone Home Manager согласовать точку подключения с
   отдельным PR и проверить обе конфигурации без активации. Реальное
   переключение на машинах обсуждается отдельно.

Следующий шаг: выбрать источник конфигурации и способ локального редактирования,
затем подготовить общую интеграцию с проверками, не включая её на машинах.
